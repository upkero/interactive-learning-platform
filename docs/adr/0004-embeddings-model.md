# ADR-0004. Модель эмбеддингов для поиска виджетов

- Статус — Предложено
- Дата — 2026-11-26
- Затрагивает SCRUM-78, 2.3, 2.3.1, 2.4.1 и 2.8

## Контекст

Резолвер ищет в библиотеке до пяти подходящих виджетов по намерению директивы.
Модель кодирует намерение и описания одинаково, без ролей запроса и документа.
Для обеих моделей нужны векторы размерности 1024 в колонке
`widget_descriptions.embedding`. У Voyage используется `input_type=None`.

Сравниваем локальную **BAAI/bge-m3** через Sentence Transformers на CPU и
**Voyage `voyage-3.5`** через API. BGE требует около 2,27 ГБ для файла весов
и не передаёт тексты внешнему провайдеру. Voyage требует ключ и передаёт ему
открытый эталонный корпус. [Веса BGE](https://huggingface.co/BAAI/bge-m3/blob/main/model.safetensors)

## Корпус и замер

В `backend/evals/data/search_library.jsonl` находятся 60 виджетов и 240
англоязычных описаний, по четыре на виджет. Данные включают три примера
из тестового каталога three-frame, шесть конфигураций из dev seed и 51
сценарий с вручную заданными параметрами. Поля `source` и `config` сохранили
происхождение и параметры сценариев. Экспорт рабочего каталога на момент
сборки пуст. Ручные сценарии описывают виджеты для стенда поиска.

В `backend/evals/data/search_intents.jsonl` находятся 150 намерений с
разметкой ожидаемого `widget_id`, включая 50 запросов на русском к
английским описаниям. Ещё 30 намерений не имеют подходящего виджета и
проверяют отсечение. Калибровочная и контрольная выборки содержат по 75
положительных запросов, из которых 25 межъязыковых, и по 15 запросов без
ответа. Запросы к одному виджету целиком входят в одну выборку.

Обе модели обрабатывают 420 текстов за один проход на одинаковых входах.
Скрипт использует `WidgetSearchRepository` на временных таблицах pgvector,
с HNSW-индексом как у приложения и `overfetch=40`, без подсказки примитива.
Поиск возвращает пять разных виджетов. Фильтрация по расстоянию выполняется
после поиска. Redis в замере не задействован.

- Recall@1 и Recall@5 показывают долю положительных запросов с верным виджетом
  на первом месте и в первой пятёрке. MRR@5 — среднее значение обратного ранга,
  где промах даёт ноль. Межъязыковые показатели приводятся отдельно.
- p95 — время одного вызова для 32 текстов после инициализации модели,
  включая сетевой вызов у Voyage. Из 14 батчей измеряются все 13 полных.
  Для сравнения задержки оба прогона выполняются на одном CPU-хосте.
- Порог `SOLVER_SEARCH_MAX_DISTANCE` — наименьшее значение с точностью до
  четырёх знаков, которое сохраняет все верные попадания в top-5 на
  калибровке. Скрипт проверяет его на контрольной выборке и сравнивает с
  исходным `0.55`. Для запросов без ответа выводится доля, где прошёл
  хотя бы один кандидат.
- Стоимость API Voyage рассчитывается по `total_tokens` из успешных ответов
  и тарифу $0.06 за миллион токенов на 2026-11-26. План показывает
  ориентир $0.00216 за один прогон из 14 запросов, считая один токен на
  байт UTF-8 и два дополнительных токена на каждый текст. Фактические
  списания зависят от биллинга и бесплатного остатка. Такой же прогон BGE
  не расходует API-бюджет. [Тарифы Voyage](https://docs.voyageai.com/docs/pricing)
- Сравнение выбирает BGE, если выигрыш Voyage по Recall@5 на контрольной
  выборке без порога меньше 5 процентных пунктов. При выигрыше от 5
  процентных пунктов включительно скрипт рекомендует Voyage. Изменение
  модели и порога утверждается после проверки результатов.

### Воспроизведение

Подойдёт отдельная PostgreSQL с включённым pgvector ≥ 0.8. Миграции
приложения не требуются. Пример запуска из корня репозитория:

```sh
docker run -d --rm --name ilp-embedding-benchmark-db \
  -e POSTGRES_HOST_AUTH_METHOD=trust -p 127.0.0.1:55432:5432 pgvector/pgvector:pg17
docker exec ilp-embedding-benchmark-db pg_isready -U postgres
docker exec ilp-embedding-benchmark-db psql -v ON_ERROR_STOP=1 -U postgres \
  -c 'CREATE EXTENSION IF NOT EXISTS vector'

cd backend
uv sync --locked --extra embeddings-local --extra embeddings-voyage
export DB_URL=postgresql+asyncpg://postgres@127.0.0.1:55432/postgres
uv run --no-sync python -m evals.embeddings_benchmark --plan

EMBEDDINGS_PROVIDER=bge_m3 EMBEDDINGS_DEVICE=cpu \
  uv run --no-sync python -m evals.embeddings_benchmark > /tmp/bge-m3.json
```

Для BGE нужен доступ к Hugging Face на первой загрузке или заранее
подготовленный кэш `HF_HOME`. Для Voyage задайте `VOYAGE_API_KEY` через
окружение, затем явно разрешите расход. В одном прогоне скрипт делает до
14 вызовов без автоматических повторов. JSON включает дату, параметры
хоста, SHA-256 корпуса, метрики и расход токенов.

```sh
EMBEDDINGS_PROVIDER=voyage \
  uv run --no-sync python -m evals.embeddings_benchmark --allow-voyage > /tmp/voyage-3.5.json
uv run --no-sync python -m evals.embeddings_benchmark --compare /tmp/bge-m3.json /tmp/voyage-3.5.json
docker stop ilp-embedding-benchmark-db
```

| voyage-3.5, API | — | — | — | — | — | — | ожидается замер |

В среде проверки установлены зависимости для BGE, загрузка весов с
Hugging Face блокируется сетевым прокси HTTP 403 и локального кэша весов
нет. Прогон Voyage требует ключа и разрешения на API-вызовы. Стенд
проверен с тестовыми векторами на PostgreSQL 17 и pgvector 0.8.7.

## Текущее решение

`EMBEDDINGS_PROVIDER=bge_m3` остаётся предварительным значением по
умолчанию. Исходный `SOLVER_SEARCH_MAX_DISTANCE=0.55` используется до
калибровки. Для принятия ADR нужны два модельных прогона и ревью Лида.

Смена модели требует пересчитать все описания в одном пространстве до
возобновления поиска. При переключении приостановите потребителей поиска,
задайте выбранную модель и выполните из корня репозитория:

```sh
docker compose --env-file backend/.env -f infra/compose.yml run --rm worker python -m src.cli reembed-descriptions
```

Воркеры должны возобновить поиск с той же моделью. Ключ
`emb:{model}:{sha256(text)}` разделяет кэш разных моделей.
