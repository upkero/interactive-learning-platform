# ADR-0004. Модель эмбеддингов для поиска виджетов

- Статус — Принято
- Дата решения Lead — 2026-11-28
- Затрагивает SCRUM-78, 2.3, 2.3.1, 2.4.1 и 2.8

## Контекст

Резолвер ищет в библиотеке до пяти подходящих виджетов по намерению директивы.
Модель кодирует намерение и описания одинаково, без ролей запроса и документа.
Для обеих моделей нужны векторы размерности 1024 в колонке
`widget_descriptions.embedding`. У Voyage используется `input_type=None`.

Для стори 2.3 выбрана локальная **BAAI/bge-m3** через Sentence Transformers
на CPU. **Voyage `voyage-3.5`** рассматривался как платная API-альтернатива,
но его запуск не выполнялся и оплата API не согласовывалась. BGE требует
около 2,27 ГБ для файла весов и не передаёт тексты внешнему провайдеру.
Voyage требует ключ и передаёт ему открытый эталонный корпус.
[Веса BGE](https://huggingface.co/BAAI/bge-m3/blob/main/model.safetensors)

## Корпус и замер

В `backend/evals/data/search_library.jsonl` находятся 60 виджетов и 240
англоязычных описаний, по четыре на виджет. Данные включают три примера
из тестового каталога three-frame, шесть конфигураций из dev seed и 51
сценарий с вручную заданными параметрами. Поля `source` и `config` сохранили
происхождение и параметры сценариев. Экспорт рабочего каталога на момент
сборки пуст. Ручные сценарии описывают виджеты для стенда поиска.

В `backend/evals/data/search_intents.jsonl` находятся 150 намерений с
разметкой ожидаемого `widget_id`, включая 50 запросов на русском к
английским описаниям. Ещё 30 намерений не имеют подходящего виджета и
проверяют отсечение. Калибровочная и контрольная выборки содержат по 75
положительных запросов, из которых 25 межъязыковых, и по 15 запросов без
ответа. Запросы к одному виджету целиком входят в одну выборку.

Скрипт поддерживает обработку 420 текстов за один проход на одинаковых
входах. Зафиксированный прогон выполнен для BGE-M3. Скрипт использует
`WidgetSearchRepository` на временных таблицах pgvector, с HNSW-индексом
как у приложения и `overfetch=40`, без подсказки примитива. Поиск возвращает
пять разных виджетов. Фильтрация по расстоянию выполняется после поиска.
Redis в замере не задействован.

- Recall@1 и Recall@5 показывают долю положительных запросов с верным виджетом
  на первом месте и в первой пятёрке. MRR@5 — среднее значение обратного ранга,
  где промах даёт ноль. Межъязыковые показатели приводятся отдельно.
- p95 — время одного вызова для 32 текстов после инициализации модели.
  Для варианта Voyage в эту задержку включался бы сетевой вызов. Это
  задержка пакетного кодирования, а не задержка поиска. В зафиксированном
  прогоне BGE из 14 батчей измерен 13 полный. При будущем сравнении оба
  прогона должны выполняться на одном CPU-хосте; Voyage-прогон не выполнялся.
- Порог `SOLVER_SEARCH_MAX_DISTANCE` — наименьшее значение с точностью до
  четырёх знаков, которое сохраняет все верные попадания в top-5 на
  калибровке. Скрипт проверяет его на контрольной выборке и сравнивает с
  исходным `0.55`. Для запросов без ответа выводится доля, где прошёл
  хотя бы один кандидат.
- Гипотетическая оценка одного Voyage-прогона рассчитана по оценке
  `total_tokens` и тарифу $0.06 за миллион токенов на 2026-11-26.
  Невыполненный план предполагал 14 API-запросов при `batch=32`
  и дал ориентир $0.00216, считая один токен на байт UTF-8 и два
  дополнительных токена на каждый текст. Это не фактические расходы: Voyage
  API не вызывался, платный API не согласован. Такой же прогон BGE не
  расходует API-бюджет.
  [Тарифы Voyage](https://docs.voyageai.com/docs/pricing)
- Правило выбора требовало, чтобы для замены BGE на Voyage был показан
  выигрыш не менее 5 процентных пунктов по Recall@5 на контрольной выборке
  без порога. Изменение модели и порога утверждается после проверки
  результатов.

### Воспроизведение

Подойдёт отдельная PostgreSQL с включённым pgvector ≥ 0.8. Миграции
приложения не требуются. Пример запуска из корня репозитория:

```sh
docker run -d --rm --name ilp-embedding-benchmark-db \
  -e POSTGRES_HOST_AUTH_METHOD=trust -p 127.0.0.1:55432:5432 pgvector/pgvector:pg17
docker exec ilp-embedding-benchmark-db pg_isready -U postgres
docker exec ilp-embedding-benchmark-db psql -v ON_ERROR_STOP=1 -U postgres \
  -c 'CREATE EXTENSION IF NOT EXISTS vector'

cd backend
uv sync --locked --extra embeddings-local --extra embeddings-voyage
export DB_URL=postgresql+asyncpg://postgres@127.0.0.1:55432/postgres
uv run --no-sync python -m evals.embeddings_benchmark --plan

EMBEDDINGS_PROVIDER=bge_m3 EMBEDDINGS_DEVICE=cpu \
  uv run --no-sync python -m evals.embeddings_benchmark > /tmp/bge-m3.json
```

Для BGE нужен доступ к Hugging Face на первой загрузке или заранее
подготовленный кэш `HF_HOME`. Для будущего согласованного Voyage-прогона
задайте `VOYAGE_API_KEY` через окружение, затем явно разрешите расход. В
одном прогоне скрипт делает до 14 вызовов без автоматических повторов.
JSON включает дату, параметры хоста, ревизию модели, SHA-256 корпуса,
метрики и расход токенов. SHA-256 корпуса вычисляется по JSONL с
нормализованными окончаниями строк CRLF→LF, поэтому одинаковый корпус
имеет одинаковый хэш на Windows и Linux.

```sh
EMBEDDINGS_PROVIDER=voyage \
  uv run --no-sync python -m evals.embeddings_benchmark --allow-voyage > /tmp/voyage-3.5.json
uv run --no-sync python -m evals.embeddings_benchmark --compare /tmp/bge-m3.json /tmp/voyage-3.5.json
docker stop ilp-embedding-benchmark-db
```

Команды Voyage описывают невыполненный план, а не состоявшийся прогон. API
не вызывался, метрики и фактические расходы отсутствуют.

| voyage-3.5, API (запуск не выполнялся) | — | — | — | — | — | — | н/д |

BGE измерили 27 ноября 2026 на GitHub Actions (`ubuntu-latest`, Linux
x86_64, 4 логических CPU, `OMP_NUM_THREADS=2` и `MKL_NUM_THREADS=2`,
PostgreSQL 17 с pgvector). Зафиксированная ревизия весов —
`5617a9f61b028005a4858fdac845db406aefb181`, SHA-256 файла
`pytorch_model.bin` — `b5e0ce3470abf5ef3831aa1bd5553b486803e83251590ab7ff35a117cf6aad38`.
SHA-256 корпуса — `1988d0dafeb81d97533dacedd0811054f226adff5d8a3aab165646bfd1d624a0`.
Указанное время относится к этому раннеру. [Коммит замера](https://github.com/upkero/interactive-learning-platform/commit/7d9a687c49df49332df25a834b657803634d04da) · [Прогон](https://github.com/upkero/interactive-learning-platform/actions/runs/46061264626) · [JSON и параметры стенда](https://github.com/upkero/interactive-learning-platform/actions/runs/46061264626/artifacts/15228004741)

На тестовой (контрольной) выборке BGE нашёл нужный виджет в top-5 для 73
из 75 намерений. Recall@1, Recall@5 и MRR@5 совпали в трёх режимах — без
порога, с исходным порогом `0.55` и с откалиброванным `0.4449`.
Порог `0.4449` пропустил кандидатов для 12 из 15 запросов без
подходящего виджета на контрольной выборке, исходный порог — для 15
из 15. Значит, даже после калибровки для 80% запросов без подходящего
виджета переранжировщик получит кандидатов.

Даже идеальный Voyage дал бы на этой выборке максимум `+2/75`, или 2.67
процентного пункта Recall@5. Следовательно, BGE-only удовлетворяет правилу
по доказанному верхнему выигрышу: доказанного преимущества Voyage не менее
5 процентных пунктов нет. Это не означает, что Voyage фактически хуже: его
сравнительные метрики и порог не измерялись.

### p95 векторного поиска

p95 векторного поиска измерен отдельно от пакетного кодирования. Значение
`2.963997` с в таблице выше относится только к embedding-батчу и не является
latency поиска.

Замер привязан к commit `d5784be22913c74fd2b570f598171c878eec203c`.
Harness:
`backend/tests/integration/db/test_widget_search_repository.py::test_explain_of_search_uses_hnsw_index`
с `ILP_MEASURE_WIDGET_SEARCH_LATENCY=1`. Использованы production threshold
`0.4449`, `k=5`, `overfetch=40` и `hnsw.ef_search=100`; для каждого hint
выполнены 5 warmup- и 100 timed-запросов, p95 вычислен методом nearest-rank.
Synthetic seed `Random(7)`: 200 виджетов, 1000 описаний, 180 активных.
Три независимых run дали:

| Hint | Run 1 p95, мс | Run 2 p95, мс | Run 3 p95, мс | Median, мс | Max, мс |
|---|---:|---:|---:|---:|---:|
| `None` | 13.019 | 13.403 | 13.216 | 13.216 | 13.403 |
| `three-frame` | 14.113 | 14.388 | 14.342 | 14.342 | 14.388 |
| `key-terms` | 31.107 | 31.172 | 31.091 | 31.107 | 31.172 |

**Вердикт: PASS.** Worst p95 — `31.172` мс, что ниже критерия `50` мс; запас
составляет `18.828` мс. Все 8 integration tests в
`test_widget_search_repository.py` прошли с `-W error`; HNSW Index Scan
подтверждён. Отдельно покрыт случай `hnsw.ef_search=150`.

Окружение — локальный Docker proxy на Windows 11 (Docker Engine 28.4.0),
PostgreSQL 17.9 с pgvector 0.8.2, Redis 7.4.12, SQLAlchemy 2.1.5 и Python
3.12.16. Измерен только service-level путь PostgreSQL/HNSW с fake embedding;
latency реального embedding, HTTP и Redis в него не входят. Это не
end-to-end latency и не замер на VPS или production-like корпусе.

Решение Lead от 2026-11-28 допускает CI/local proxy для закрытия критерия
p95 < 50 мс в этой истории и явно фиксирует отклонение от требования измерить
search latency на целевом VPS. Условие VPS-критерия этим замером не считается
выполненным. Целевой VPS/production-like benchmark с реальными BGE embeddings
можно выполнить позже; он не блокирует текущее решение.

## Текущее решение

`EMBEDDINGS_PROVIDER=bge_m3` используется по умолчанию. BGE-M3 — локальная
модель, поэтому стоимость embedding составляет $0. Runtime закрепляет
ревизию весов BGE-M3 через `EMBEDDINGS_REVISION` со значением
`5617a9f61b028005a4858fdac845db406aefb181`; это та же ревизия, на которой
получены зафиксированные результаты. Для BGE порог
`SOLVER_SEARCH_MAX_DISTANCE` равен `0.4449`. Если в окружении явно задано
прежнее значение `0.55`, измените его для BGE. ADR принят Lead
2026-11-28.

Voyage AI API не выполнялся; платный API не согласован, метрики — н/д,
запуск отсутствует. Voyage не обязателен для стори 2.3. Буквальная
процедура «прогнать обе модели» не выполнена и является осознанным
отклонением, разрешённым Lead для стори 2.3. Будущий Voyage-эксперимент —
отдельное решение с согласованием оплаты и re-embedding.

Смена модели или ревизии BGE-M3 требует пересчитать все описания в одном
пространстве до возобновления поиска. При переключении приостановите
потребителей поиска, задайте выбранную модель и ревизию и выполните из
корня репозитория:

```sh
docker compose --env-file backend/.env -f infra/compose.yml run --rm worker python -m src.cli reembed-descriptions
```

Воркеры должны возобновить поиск с той же моделью и ревизией. Ключ
`emb:{model}:{revision}:{sha256(text)}` разделяет кэш разных моделей и
ревизий. Старые ключи без ревизии становятся cache miss и безопасно
пересчитываются. Миграция БД не требуется: текущие векторы созданы
текущей ревизией; при её смене reembed обязателен.
